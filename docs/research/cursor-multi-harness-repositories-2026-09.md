# Cursor support in multi-harness usage trackers

Research date: 2026-09-10. This is a source inspection, not a live Cursor account experiment. No downloaded programs were executed and no local credentials were read.

## Result

Existing multi-harness trackers already import historical Cursor token usage through authenticated dashboard endpoints. Several implementations read Cursor's local SQLite database **for authentication**, then fetch usage remotely. Describing these as local transcript or token parsers would be inaccurate. The strongest discovered session-attribution lead is tokscale's September 2 switch from CSV to JSON: its parser reads `conversationId`, and the change author reports a live sync containing 34 events across 18 real Cursor sessions. This establishes a concrete integration path worth validating. It does not establish workspace or machine attribution, complete history retention, or a stable supported public API contract. [Tokscale change and live report](https://github.com/junhoyeo/tokscale/pull/1247), [TokenTracker auth and API implementation](https://github.com/xiufengsun/TokenTracker/blob/f15ca22b458e84fc8ad6a545a8d4d5ed4b915307/src/lib/cursor-config.js), [aitrack reader](https://github.com/bircni/aitrack/blob/53fc7365803c38a5ceee77af6237227a9efd7e6e/packages/aitrack-lib/src/readers/cursor/index.ts).

The repository evidence narrows the difficulty: account usage is feasible today; the unresolved work is validating its meaning and coverage, joining local workflow identity, and preventing account-wide records from being counted once per machine. Reverse engineering is an identifiable maintenance dependency, not a sufficient reason to dismiss the integration.

## What the strongest evidence actually establishes

### Conversation IDs are a concrete lead

Tokscale's JSON parser maps `conversationId` directly into `session_id`; missing IDs use an account/day synthetic identifier. The upstream PR says a real sync returned 34 events, 18 sessions, including `bc-` background-composer IDs, with per-session costs matching summed charged cents. That is a maintainer-reported live experiment plus an inspectable implementation. It is stronger than a README claim, but this research did not reproduce it. Nothing in the inspected parser proves that the ID matches every local composer ID or hook `conversation_id` across IDE, CLI and background agents. [PR report](https://github.com/junhoyeo/tokscale/pull/1247), [parser and tests](https://github.com/junhoyeo/tokscale/blob/4b343e43bf0f1aa78f5032cb082f1c2c4cc76f65/crates/tokscale-core/src/sessions/cursor.rs).

The same change's commit message says the later `totalCents` parity exercise had no real JSON available on that development machine and generated part of its fixture from CSV. This caveat applies to that cost validation, not a retraction of the PR's earlier live conversation-ID report. The pricing parity result is therefore weaker than independent raw JSON-versus-dashboard measurement. [Merged commit with validation caveats](https://github.com/junhoyeo/tokscale/commit/829124d970a87516299005b9b637a010c019f039).

### Token columns have already caused silent miscounting

Tokscale and tokenleak now treat `Input (w/ Cache Write)` and `Input (w/o Cache Write)` as disjoint buckets. CodexBar's JSON interpretation agrees: uncached input, output, cache-write and cache-read are separate counters. TokenTracker and tokctl still compute cache write as the first CSV input column minus the second. This observable disagreement is a warning against implementing by popularity or copying an adapter unchanged. The validation fixture must reconcile the four counters against native `Total Tokens`, and must include nonzero uncached input and nonzero cache writes. [Tokscale bucket correction](https://github.com/junhoyeo/tokscale/commit/fd26e4e6d07747bb95a431cb6232d9724d7ba029), [tokenleak mapping](https://github.com/ya-nsh/tokenleak/blob/fd38fa290d7cd4e317b95401f42a4aa2f3779808/packages/registry/src/providers/cursor.ts), [TokenTracker conflicting mapping](https://github.com/xiufengsun/TokenTracker/blob/f15ca22b458e84fc8ad6a545a8d4d5ed4b915307/src/lib/cursor-config.js), [tokctl conflicting mapping](https://github.com/adamthuvesen/tokctl/blob/9151f6e6dad69c61dc341fe39e5496a8c4f501b7/src/sources/cursor.rs).

The maintained tokscale history documents a specific schema regression: Cursor v3 added Cloud Agent ID and Automation ID columns, moving a positional parser's token and cost fields. The April 15 fix describes token inflation and missing April 9 data. This is evidence of actual maintenance cost, rather than a hypothetical assertion that all undocumented formats are unusable. [CSV v3 fix](https://github.com/junhoyeo/tokscale/commit/fe73fdc3e7eac51f8cd7da9b772908423f2dbffb).

### Zero, missing, included and estimated are different states

Tokscale makes token fields optional and then defaults absent counters to zero. CodexBar preserves missing versus invalid **cost**, but its numeric token helper also produces integer counters. Receipts maps malformed/missing counters to zero. These implementations therefore establish that counters can be consumed, not that every emitted zero proves zero measured usage. An AI Stack adapter should preserve absent `tokenUsage` as unmeasured, and test missing versus explicit-zero fields before choosing normalization semantics. [Tokscale parser](https://github.com/junhoyeo/tokscale/blob/4b343e43bf0f1aa78f5032cb082f1c2c4cc76f65/crates/tokscale-core/src/sessions/cursor.rs), [CodexBar cost-state decoder](https://github.com/steipete/CodexBar/blob/3b6864fa92489b7df122e72c153a579db4c0ddd8/Sources/CodexBarCore/Providers/Cursor/CursorUsageEventsFetcher.swift), [receipts parser](https://github.com/ChrBoebel/bb-plugin-receipts/blob/88faf798a6feb277c61f15c9e4e99145d785a430/lib/cursor-api.ts).

`chargedCents` and `tokenUsage.totalCents` have different intended meanings in these codebases. CodexBar exposes the plan-deducted amount separately from token cost; tokscale prioritizes `totalCents` for usage valuation; receipts prioritizes `chargedCents`. Plan-included use must continue counting tokens even if the wallet debit is zero. A TokenTracker user reported Enterprise Cursor tokens disappearing from the main total after using Claude Code, and its normalization now explicitly keeps included tokens in the headline. [CodexBar cost handling](https://github.com/steipete/CodexBar/blob/3b6864fa92489b7df122e72c153a579db4c0ddd8/Sources/CodexBarCore/Providers/Cursor/CursorUsageEventsFetcher.swift), [TokenTracker user report](https://github.com/xiufengsun/TokenTracker/issues/106).

`model` can be a routing label such as `auto` or `agent_review`, not the underlying vendor model. Tokscale's change explicitly refuses to infer the real model from adjacent conversation rows, because there is no per-request model mapping in the export it examined. Tokens can be measured while model attribution and catalog-derived pricing remain unknown. No inspected adapter exposes cache-write TTL or separate reasoning-token counters as native Cursor facts. [Tokscale change rationale](https://github.com/junhoyeo/tokscale/commit/829124d970a87516299005b9b637a010c019f039).

### Deduplication is not solved by a timestamp or conversation ID

CodexBar explicitly documents that the endpoint exposes no stable event ID in its inspected shape. It gathers pages, compares their counts with `totalUsageEventsCount`, and removes matching adjacent-page overlap only when the advertised count proves extra rows exist. Equal rows remain distinct when the count includes both. By comparison, receipts probes `id`, `usageEventId` and `requestId`, then hashes fields and drops repeats. The latter's optional names are defensive guesses in source, not evidence that Cursor supplies a stable event ID. Hashing can collapse legitimate identical events. A conversation contains multiple billable events, so `conversationId` alone cannot deduplicate usage. [CodexBar pagination](https://github.com/steipete/CodexBar/blob/3b6864fa92489b7df122e72c153a579db4c0ddd8/Sources/CodexBarCore/Providers/Cursor/CursorUsageEventsFetcher.swift), [receipts event key](https://github.com/ChrBoebel/bb-plugin-receipts/blob/88faf798a6feb277c61f15c9e4e99145d785a430/lib/cursor-api.ts).

Tokscale additionally handles duplicate JSON/CSV account caches and account switching, refuses incomplete pagination or suspicious zero-event replacement, and archives legacy CSV history. Its JSON fetch requests `teamId: 0`, page and page size, without explicit start/end bounds. That proves a paginated fetch of the endpoint's current result set, not a guarantee of unlimited historical retention. TokenTracker preserves buckets older than the earliest returned date, explicitly anticipating future windowing or truncation. Neither behavior establishes that an arbitrary old day can be recovered from Cursor. [Tokscale cache implementation](https://github.com/junhoyeo/tokscale/blob/4b343e43bf0f1aa78f5032cb082f1c2c4cc76f65/crates/tokscale-cli/src/cursor.rs), [TokenTracker historical replacement](https://github.com/xiufengsun/TokenTracker/blob/f15ca22b458e84fc8ad6a545a8d4d5ed4b915307/src/lib/rollout.js).

## Implications for AI Stack and remaining experiments

These are research conclusions and proposed validation work, not an implementation decision:

1. **Account-level history is feasible.** Evaluate authenticated JSON usage import before restricting personal support to prospective hooks. A manual CSV import also has multiple implemented precedents.
2. **Conversation joins are now a specific experiment.** Collect one IDE conversation, one CLI conversation and one background-agent conversation; compare dashboard `conversationId`, local storage identifiers and hook identifiers. Include `bc-` IDs, resumed chats and subagents. Report unmatched events rather than constructing a session from the timestamp.
3. **Preserve scope.** The demonstrated usage feed is account-wide. Importing it on each machine into AI Stack's machine/day rows risks duplicate counting and wrong machine attribution. None of the inspected adapters demonstrates a trustworthy machine field. This needs either a proven local join or account-level ingestion ownership and deduplication semantics.
4. **Reconcile raw counters and monetary meanings.** Use native JSON and CSV from the same bounded window; retain `Kind`, `isTokenBasedCall`, `chargedCents`, `totalCents`, raw model, optional counters and reported totals. Include plan-included, errored/no-charge, routing-label, missing-cost, cache-write and refund cases. Record which fields are truly absent.
5. **Measure history coverage explicitly.** Test an old billing period, an account switch, records arriving during pagination and a partial fetch. Track coverage dates and failure status; retain prior good snapshots. A cache file's existence does not establish complete history.
6. **Keep workflow claims separate from usage claims.** These eight implementations demonstrate token/cost ingestion, and one demonstrates a real conversation-ID mapping with a live report. They do not establish tool-call semantics, per-call context, workspace, repository, or machine joins for AI Stack's measured workflow rules.

The major remaining unknown is no longer whether open-source projects can import Cursor usage. They can. The remaining unknown is whether the specific identifiers and counters can meet AI Stack's attribution and measurement requirements across the Cursor variants it intends to support.
